# 재검사 판단 평가 — v0.2.1

## 이전 과제가 차이를 못 드러낸 이유

v0.2 비교는 6개 짧은 상황에서 다음 행동과 완료 여부를 답하는 과제였다. 실제 파일 편집은 제목 변경 한 건뿐이었다. 단서가 명확하고 평가도 거칠어 두 버전 모두 통과했다. 이는 효과가 없다는 증명도, 효과가 있다는 증명도 아니다. 실행 경로와 불필요한 검사를 직접 관찰하는 과제가 필요했다.

## 기존 벤치마크를 먼저 검토

| 기존 프로젝트 | 적합한 측정 | 이번 사용 여부와 이유 |
| --- | --- | --- |
| [SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) | 고정된 실제 저장소·요구·실행 검증으로 스킬 유무 비교 | 후속 실제 코딩 평가 후보. 논문 초록/저장소 정보 확인, 이번 실행 안 함. 전체 실행 비용이 $0.30 이내라는 보장은 없음 |
| [SkillsBench / BenchFlow](https://github.com/benchflow-ai/benchflow/blob/main/docs/skill-eval.md) | 스킬 유무, 실행 흔적, 다양한 과제 비교 | 기존 하네스 후보. 기본 흐름에 에이전트와 LLM 판정 비용이 있어 이번 강한 예산 제한에서는 실행 안 함 |
| [agent-skill-eval](https://github.com/tardigrde/agent-skill-eval) | 실제 Codex 등 CLI의 반복 비교, 토큰·비용·시간 | 비용 가드는 실행 후 검사라고 문서에 명시. 단독으로는 $0.30의 호출 전 상한 보장 수단이 아님 |

이번에는 위 프로젝트의 코드나 데이터셋을 복사하지 않았다. 좁은 예산 안에서 실제 모델 선택과 검사 실행을 연결하기 위해 표준 Python만 사용하는 **한 개의 제한된 실험 스크립트**를 작성했다. 범용 평가 엔진이나 제품 의존성이 아니며, 장기 코딩 평가에는 위 기존 하네스를 우선한다.

## 이번 과제: 실행 증거를 재사용할지 결정

모델은 현재 숫자 데이터, 환경 표식, CSV/HTML 결과와 실행 영수증을 받는다. `check public`은 실제 메모리상 CSV 생성·파싱과 HTML 비교를 실행하고, `check unit`은 합계 컴포넌트만 확인한다. `finish`는 합계와 영수증 ID를 제출한다. 모델이 임의 코드를 작성하거나 셸을 사용하는 과제는 아니다. 제품 전체의 실제 웹 경로도 아니므로 **제한된 행동 공간의 재검사 마이크로벤치마크**라고 부른다.

| 상태 | 완료에 필요한 증거 | 최소 추가 검사 |
| --- | --- | --- |
| fresh | 현재 데이터·환경·아티팩트와 일치하는 public 검사 영수증이 이미 존재 | 0 |
| data_changed | 데이터에 숫자가 추가됐지만 이전 결과·영수증만 존재 | public 1회 |
| environment_changed | 관련 환경 표식이 달라졌지만 이전 영수증만 존재 | public 1회 |
| unit_only | 컴포넌트 검사만 있고 CSV/HTML 결과 검증이 없음 | public 1회 |

주평가: 올바른 합계와 현재 상태에 유효한 **최신 public 영수증**을 제출했는가. 부평가: 검사 횟수, 유효한 public 증거가 있는데 실행한 중복 검사, 목적에 필요 없는 unit 검사, API 토큰과 비용. 중복과 불필요 unit은 겹칠 수 있으므로 합산하지 않는다. 최신 영수증만 유지하는 제한과 정확한 ID 복사가 판정에 영향을 줄 수 있다. 실제 프로젝트의 모든 증거 저장 방식을 대표하지 않는다.

스킬 없음 / v0.2 / 수정안, 4상태 × 2반복으로 총 24회. 순서는 고정 seed로 섞었고 각 에피소드는 독립 API 문맥이다. 이 seed는 실행 순서만 정하며 모델 샘플링을 고정하지 않는다. temperature는 별도 지정하지 않았다. 각 에피소드 최대 3응답. 조건·규칙·판정은 첫 호출 전에 고정했으며 결과를 본 뒤 스킬을 조정하거나 유리한 결과가 나올 때까지 재실행하지 않았다. 로컬 판정기만 사용하며 유료 LLM 판정기는 없다. 입력에 상태를 명시한 작은 인공 과제이며, 장기 문맥·자율 코딩·실제 사용자 상호작용을 검증하지 않는다.

## 결과: 작은 차이는 관찰됐지만 일반 효과는 미확인

| 조건 | 성공 | 전체 검사 | 중복 검사 | 중복 또는 불필요 unit 검사 | 추정 API 비용 |
| --- | --- | --- | --- | --- | --- |
| 스킬 없음 | 3/8 | 4 | 1 | 3 | $0.00213060 |
| v0.2 | 3/8 | 6 | 2 | 4 | $0.00483520 |
| v0.2.1 수정안 | 5/8 | 6 | 1 | 3 | $0.00492815 |

모든 조건이 fresh를 2/2 통과했고 data_changed는 1/2였다. 수정안은 environment_changed와 unit_only에서 각각 1/2, 다른 두 조건은 각각 0/2였다. 수정안의 실패 3건은 변경된 데이터의 이전 합계를 제출, 환경이 바뀐 영수증 재사용, unit 검사만으로 완료였다. 따라서 ‘재검사를 줄여도 안전해졌다’거나 ‘비용 절감’이라고 결론내리지 않는다. 수정안의 전체 검사 횟수는 줄지 않았고 API 비용은 v0.2보다 약 1.9% 늘었다. 스킬 없음보다도 비용이 높다. 8회씩의 관찰 차이는 안정적인 향상이나 심리적 기제의 증거가 아니다.

응답 모델은 `gpt-5.4-nano-2026-03-17`, reasoning none. **40 API 호출, 입력 49,326 / 출력 1,623 토큰, 합계 $0.01189395**. 캐시 할인을 적용하지 않은 공식 단가 계산이며 청구서 확정액은 아니다. 이번 추가 모델 실험의 API 비용이며 이 대화의 구독 사용량·개발 시간·로컬 계산비용을 포함한 총원가가 아니다. [사용 단가](https://developers.openai.com/api/docs/models/gpt-5.4-nano).

검사기 자체는 네 개의 로컬 unittest(변경 상태 3종의 하위 사례 포함)로 검사했다. 이는 모델 성능과 별개다. 합성 입력과 모든 24회 행동·실패·토큰 집계는 [공개 결과 JSON](../evals/recheck_results.json), 실행/판정 코드는 [recheck_probe.py](../evals/recheck_probe.py)에 있다. 키·개인 원문·인증 응답은 포함하지 않는다.

## 비용 제한과 재현

API 호출 전에 텍스트 요청의 UTF-8 바이트 수 + 프레이밍 여유 2,048을 입력 토큰의 보수적 상계로 예약하고, 최대 출력 512토큰도 예약한다. 요청은 12,000바이트 이하, 총 72호출 이하, 누적 예약은 $0.27 이하. 이 실행에서 예약 총액은 $0.0859888이었다. 예약은 사용량이 적어도 반환하지 않는다. 자동 재시도·호스팅 도구·유료 판정기는 없으며 응답 불명확/사용량 누락이면 멈춘다. [출력 상한은 비가시 토큰도 포함](https://developers.openai.com/api/docs/guides/token-counting).

이 한도는 문서화된 해당 모델의 표준 텍스트 단가와 요청 형태를 전제로 한다. 다른 모델·단가·멀티모달·클라우드 샌드박스에 그대로 적용하면 안 된다. 재실행은 별도 비용이 발생하므로 다시 승인된 예산이 있어야 한다. 키는 실행 환경의 `OPENAI_API_KEY`로만 제공하고 Git에 저장하지 않는다.

```sh
python evals/recheck_probe.py --self-test
# 아래는 유료 실행. 키를 안전하게 환경에 설정하고 단가를 재확인한 뒤에만 실행:
python evals/recheck_probe.py --run --output .codex-shared/new-evaluation
```

비교 기준은 코드에 고정된 v0.2 커밋과 현재 체크아웃의 스킬이다. 다른 버전에서 재실행하면 이번 실험과 다른 비교가 된다. 결과 디렉터리는 새 경로여야 하며 기존 예산 장부를 덮어쓰지 않는다. 표준 라이브러리만 사용하지만 이 실행으로 확인한 환경은 Windows의 로컬 Python이다.

## 반영한 수정과 다음 검증

검증 문단을 교체했다: **현재 요구·아티팩트 버전·관련 환경에 맞는 신뢰할 만한 결과는 재사용하고, 빠지거나 오래되거나 변경으로 무효화된 부분만 최소 검사한다.** 필수 검증 생략 금지가 함께 유지된다. 이번 수정은 기존에 관찰된 재검사 제안을 근거로 한 좁은 보완이다.

여기서 멈춘다. 다음 단계는 실제 프로젝트의 변경/무변경 짝과 실행 흔적을 기존 하네스에 넣는 것이다. 오늘의 비용이 작았다는 이유로 남은 예산을 소진하거나, 성공률이 높아질 때까지 규칙을 늘리지 않는다.
